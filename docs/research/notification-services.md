# Notification services for Cadence

Evidence checked 2026-11-23. Research for [Research notification services and development-to-production costs](https://github.com/ameow/cadence-project/issues/3), under [Notifications: find the way to a first-version specification](https://github.com/ameow/cadence-project/issues/1). This report supplies evidence for a later human choice; it selects no provider. No accounts were provisioned and no integration was run.

## Scope and existing application

The agreed first version covers lesson questions → owning Instructor; replies → asking Student; new Refund Requests → Platform Admins; approved/declined Refund Requests → buyer. Channels are an in-app inbox and email; SMS and push are excluded. These are planning inputs from the map, not claims about implemented triggers. [Planning map](https://github.com/ameow/cadence-project/issues/1).

At the inspected commit, Cadence already builds buyer Refund Request receipts and decision emails. Server route actions await `sendEmail`, and the transport calls Postmark directly when configured or writes JSON to `.outbox` locally. This is a useful boundary: any later orchestration must preserve those messages' purpose and assign exactly one email owner to avoid duplicates. [Mailer source](../../app/lib/mailer.server.ts), [Refund logic](../../app/lib/refunds.server.ts), [buyer route](../../app/routes/courses.$slug.refund.ts), [admin route](../../app/routes/admin.refunds.tsx). Source baseline: `979e28535d8b0ddd32b7241e51423c9a381879ad`.

## Shortlist and decision boundaries

Novu, Knock, and MagicBell merit comparison because their official interfaces cover a hosted recipient inbox plus external email delivery. The following sections distinguish documented capability from fit inferred for Cadence. SDK availability does not prove React Router server-rendering compatibility or authorization correctness; those require a later small integration check.

## Novu

- **Hosted React inbox:** `@novu/react` supplies `<Inbox />`, bell, notification list, unread count and preference UI; interactions synchronize to Novu. Headless hooks/custom components are supported. This is one-way notification infrastructure. [Inbox](https://docs.novu.co/platform/inbox)
- **Read state and preferences:** current APIs include read, unread, seen, and mark-all-read, with subscriber-scoped counts. [API index](https://docs.novu.co/_llms/api-reference.txt) The UI supports global channel preferences and workflow-specific choices; the more specific workflow preference wins. Critical workflows cannot be disabled by subscribers. [Preferences](https://docs.novu.co/platform/inbox/configuration/preferences)
- **Recipient security:** enable HMAC explicitly in the in-app integration before production. Backend computes HMAC-SHA256(secret API key, subscriber ID) and supplies `subscriberHash` to the authenticated client's Inbox. Without HMAC, another person knowing/guessing the subscriber ID and public app identifier could view that feed. With HMAC enabled, a missing hash prevents loading. Secret API key stays server-side. Context-scoped use additionally requires signed context. [Production preparation](https://docs.novu.co/platform/inbox/prepare-for-production)
- **Postmark:** native email provider integration stores a Postmark server API token and verified sender email in Novu. [Postmark setup](https://docs.novu.co/platform/integrations/email/postmark) General email activity tracking is Cloud/Enterprise self-hosted only; the activity-tracking page does not list Postmark among its manual provider guides, so precise Postmark receipt coverage needs a test/support confirmation rather than assuming parity with Knock's detailed integration. [Activity tracking](https://docs.novu.co/platform/integrations/email/activity-tracking)
- **Server event trigger:** backend sends event API request with workflow identifier, subscribers and payload, authenticated by environment secret. Production workflows must be published. Passing a recipient object can create the subscriber. [Trigger workflow](https://docs.novu.co/platform/workflow/trigger-workflow)
- **Idempotency:** documented `Idempotency-Key` support is **not enabled for every organization**; contact support. POST/PATCH using API-key authentication supported. Successful and error responses cache 24 hours; in-flight cache five minutes, duplicate in-flight request returns 409. Changed body with reused key returns 422. `transactionId` is tracing/cancellation and offers weaker deduplication/billing protection than the header. Confirm enabled behavior before relying on retries. [Idempotency](https://docs.novu.co/api-reference/idempotency)
- **Provider-send retries:** current dedicated documentation explicitly says **one attempt**, including terminal treatment of provider 429/503 responses; no automatic provider failover. Failure is recorded with provider response and `messages.failed`, then the next channel step continues. No dead-letter queue. Framework bridge calls and outbound webhooks have distinct retry policies; these do not imply email-send retries. [Delivery retry policy](https://docs.novu.co/platform/developer/delivery-retries)
- **Logs:** Activity Feed exposes workflow/step execution, payloads and provider responses. [Monitor/debug](https://docs.novu.co/platform/workflow/monitor-and-debug-workflow) Free/Pro/Team activity retention: 24h/7d/90d; inbox retention: 30d/90d/90d. [Limits](https://docs.novu.co/platform/developer/limits)
- **Outbound events/export:** Team/Enterprise gated outbound webhooks can deliver JSON events to Cadence or connectors such as warehouses, S3 and queues. This can support an external event archive; it is not evidence of a full historical account-data export. [Webhooks](https://docs.novu.co/platform/developer/webhooks)
- **Residency:** US Virginia and EU Frankfurt are available to all plans, chosen at signup; keys are region-bound. Additional UK/SG/AU/JP/KR regions are Enterprise. Moving region requires contacting Novu; changing URL alone fails authentication. [Security/residency](https://docs.novu.co/platform/additional-resources/security)
- **Free development versus production/self-hosting:** Free has Dev+Prod environments; all count toward the organization meter. Community self-hosting has no Novu license fee; Enterprise on-premises is separately licensed and adds cloud business features/support. Infrastructure and operations remain additional costs. [Billing](https://docs.novu.co/platform/account/billing) Community does not include email activity tracking. [Activity tracking](https://docs.novu.co/platform/integrations/email/activity-tracking)
- **Workflow limit:** the pricing page retrieved for this report lists five workflows on Free. The four agreed trigger families could fit only if their final workflow decomposition stays within that limit; this is not yet specified. [Pricing](https://www.novu.co/pricing/)

## Knock

- **Hosted React inbox:** current `@knocklabs/react` includes popover feed, full-page feed, notification bell with unread/unseen counts, and headless hooks. React docs link a preference center and custom preferences hooks. [React overview](https://docs.knock.app/in-app-ui/react/overview)
- **Read state:** APIs mark and unmark messages as read, seen or archived, singly or in batches. [Client security/API surface](https://docs.knock.app/in-app-ui/security-and-authentication) A JSON `PreferenceSet` controls channels, channel types, categories and workflows; Knock suppresses sends when users opt out. [Preferences](https://docs.knock.app/preferences/overview)
- **Recipient security:** enhanced security is **off by default**; turn it on before production. Backend signs RS256 JWTs with user `sub` and preferably `iat`/`exp`; client combines signed user token and public key. Tokens can carry explicit feed/preference grants and tenant scopes. Without enhanced security the public key can act as any user. Avoid assuming a public key alone authorizes a recipient. [Security/authentication](https://docs.knock.app/in-app-ui/security-and-authentication)
- **Postmark:** native provider supports attachments, environment configuration, sandboxing and Postmark/Knock open/link tracking. Incoming delivery webhooks map Delivery→delivered, Bounce→bounced and record complaints. Default stream is `outbound`; payload overrides can set `MessageStream`. Knock adds message/recipient IDs as Postmark metadata and workflow key as Tag. [Postmark integration](https://docs.knock.app/integrations/email/postmark)
- **Server trigger/idempotency:** server SDK or API triggers named workflow for recipients with data/actor/tenant; up to 1,000 explicit recipients per call. Optional `Idempotency-Key` prevents duplicate workflow runs in a 24-hour window; changed parameters error. [Trigger API](https://docs.knock.app/send-notifications/triggering-workflows/api) Only successful responses are cached; failed 4xx/5xx calls can be executed again. This header currently affects only workflow trigger endpoint. [API idempotency](https://docs.knock.app/api-reference/overview/client-libraries)
- **Send retries/logs:** network, retryable provider and transient pipeline errors retry up to eight times over 30 minutes using exponential backoff and jitter. Permanent failure becomes undelivered; bounced messages aren't retried. Undelivered messages can be retried manually in dashboard. Message detail includes provider request/response logs. [Delivery](https://docs.knock.app/send-notifications/delivering-notifications)
- **Outbound events:** environment-specific webhooks report message events to Cadence; verify HMAC-SHA256 signature/timestamp. Most non-2xx/timeouts retry over hours, except listed permanent/redirect status codes. Delivery logs contain payload/status. [Outbound webhooks](https://docs.knock.app/developer-tools/outbound-webhooks/overview)
- **Retention:** non-Enterprise message/run/source/webhook logs retain 30 days; Enterprise 90 days, universal API logs 30 days. Custom retention policies not currently supported. Inbox feed items remain available indefinitely and read-state operations keep working after diagnostic message logs expire. [Data retention](https://docs.knock.app/manage-your-account/data-retention)
- **Export:** analytics warehouse export is Enterprise-only; initial historical backfill then periodic sync. This is analytics export, not a proven complete portable export of recipients/preferences/feed histories. [Warehouse export](https://docs.knock.app/integrations/extensions/warehouse-export)
- **Free versus production/testing:** Free includes full notification channel access for small deployments. Development/production environments are isolated but delivered test messages count toward usage; sandboxed out-of-app messages don't count. In-app feed has no sandbox mode, so control tests through channel conditions. EU residency is explicitly **coming soon, expected by end 2026**; availability today needs confirmation. [Plans and usage](https://docs.knock.app/manage-your-account/knock-plans)
- **Residency/self-hosting unknown:** security docs repeat EU upcoming; reviewed official docs do not establish an available customer self-hosted edition or exact current production geography. Do not infer self-hosting from Enterprise dedicated infrastructure wording. [Security](https://docs.knock.app/developer-tools/security), [Pricing](https://knock.app/pricing)

## MagicBell

- **UI and preferences:** `@magicbell/react` provides floating or embedded inboxes, pagination, read/unread state, custom item rendering and CSS theming. `UserPreferences` toggles channels per category. This supports a standard bell or custom inbox; exact accessibility and React Router hydration behavior remain untested. [React documentation](https://www.magicbell.com/docs/libraries/magicbell-react).
- **Identity and server integration:** User JWTs bind an email or external ID and are signed on the backend with the project's secret; never expose the secret. Project JWTs authorize server API operations, and broadcasts accept explicit recipient lists. Cadence could use its stable database user ID as external ID; the backend must derive that from its session rather than browser input. [User JWT](https://www.magicbell.com/docs/api/authentication/user), [Project JWT](https://www.magicbell.com/docs/api/authentication/project), [broadcast primitive](https://www.magicbell.com/docs/primitive/broadcast).
- **Postmark:** The current channel list documents generic SMTP, not a native Postmark adapter. SMTP accepts host, credentials, sender and STARTTLS. Postmark supports transactional SMTP at `smtp.postmarkapp.com` and stream-specific SMTP tokens. Compatibility is therefore a documented-protocol inference; confirm delivery callbacks, stream selection and suppression diagnostics in a spike. [MagicBell SMTP](https://www.magicbell.com/docs/channels/email/smtp), [Postmark SMTP](https://postmarkapp.com/developer/user-guide/send-email-with-smtp).
- **Reliability and diagnostics:** API idempotency is available on some endpoints through `Idempotency-Key`, with results cached 24 hours. Its documented limit is 500 requests/minute per IP, returning 429 for 60 seconds. Dashboard events show user, notification, channel and HTTP request/response; delivery objects track attempt history and state. An exact automatic provider retry schedule was not established in the reviewed docs—do not assume one. [API](https://www.magicbell.com/docs/api), [events](https://www.magicbell.com/docs/dashboard/events), [delivery lifecycle](https://www.magicbell.com/docs/primitive/delivery).
- **Data and portability:** Vendor statements describe encryption at rest/in transit, DPA availability, portability and erasure rights. Public privacy text gives purpose-based rather than a fixed inbox retention period, with processing at operating offices/other processors. A contractual notification-data region, retention/deletion schedule and complete inbox export are unverified. OpenAPI and client components ease integration replacement but do not make hosted workflow/state export automatic; no self-hosted backend was verified. [Trust Centre](https://www.magicbell.com/security), [privacy policy](https://www.magicbell.com/privacy-policy), [OpenAPI documentation](https://www.magicbell.com/docs/api).

## Illustrative cost method

These are scenarios, not Cadence traffic forecasts: 100, 1,000 or 10,000 distinct monthly recipients, each receiving five logical notifications, each delivered once in-app and once by email. That means 500/5,000/50,000 logical recipient events and 1,000/10,000/100,000 channel deliveries, including 500/5,000/50,000 emails. Count each Platform Admin separately; one request notifying three admins consumes three recipient events. Preferences, batching, digests, suppressed emails and existing receipts change these totals. Quotes exclude tax, support, engineering, hosting and transport unless stated.

MagicBell Builder costs $0/month, includes all integrations, 1,000 deliveries and one project. Startup is $249/month for 50,000 deliveries and five projects, then $0.0025/delivery. A delivery is counted per recipient/channel, so the three scenarios are $0, $249, and $374/month for orchestration **if upgrading to Startup when above Builder**. The pricing FAQ says excess deliveries incur usage charges but does not establish Builder's excess rate; obtain confirmation instead of assuming the Startup rate applies. Multiple environments may need separate projects. [MagicBell pricing](https://www.magicbell.com/pricing).

Postmark remains a separate transport bill. Developer includes 100 emails/month indefinitely, with no overages; Basic starts at $15/month for 10,000 emails and $1.80 per extra 1,000. Using that one tier consistently for illustration gives $15/$15/$87 for 500/5,000/50,000 emails, before other Cadence mail. Higher-volume tiers may be cheaper. Thus MagicBell + that illustrative Postmark tier totals $15/$264/$461. Existing paid Postmark capacity may make the marginal cost lower; the actual plan was not inspected. [Postmark pricing](https://postmarkapp.com/pricing).

## Comparable orchestration costs and development limits

| Monthly recipients (five events each) | Novu runs | Two-channel deliveries | Novu | Knock | MagicBell |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 100 | 500 | 1,000 | $0 | $0 | $0 |
| 1,000 | 5,000 | 10,000 | $0 | $0 | $249 |
| 10,000 | 50,000 | 100,000 | $54 | $500 | $374 |

Novu meters each subscriber workflow execution, independent of channel count: Free includes 10,000 monthly runs; Pro $30 includes 30,000, then $1.20 per additional 1,000. Therefore 50,000 costs $54. Free combines development and production usage and stops at its limit with HTTP 402. Free activity logs last only 24 hours; inbox items 30 days. This volume comparison does not promise the free tier satisfies diagnostics, branding or failure-recovery requirements. [Novu billing](https://docs.novu.co/platform/account/billing), [pricing](https://www.novu.co/pricing/), [limits](https://docs.novu.co/platform/developer/limits).

Knock counts successful recipient/channel messages; Free includes 10,000, Starter $250 includes 50,000 then $0.005/message. Thus 100,000 costs $500. It describes Free as usable for small deployments, retains branding, and does not hard-stop excess Free usage: the vendor contacts the account about billing. Tests across environments also consume allowance unless an out-of-app channel is sandboxed; in-app cannot be sandboxed. [Knock pricing](https://knock.app/pricing), [plans/usage](https://docs.knock.app/manage-your-account/knock-plans).

Adding the illustrative Postmark Basic transport amounts above produces Novu totals $15/$15/$141 and Knock totals $15/$15/$587. Novu failure-event webhooks require Team or Enterprise; if the later recovery design depends on those webhooks, the $54 Pro illustration is not an adequate feature quote. Team starts $250/month. These figures compare explicitly stated plans, not the cheapest negotiated or optimized contract. [Novu webhooks](https://docs.novu.co/platform/developer/webhooks), [Novu pricing](https://www.novu.co/pricing/), [Knock pricing](https://knock.app/pricing), [Postmark pricing](https://postmarkapp.com/pricing).

## What the provider cannot decide for Cadence

These are integration implications inferred from the scope and APIs, not an implementation plan or settled product policy:

1. Resolve recipients in Cadence's server: current course ownership, question author, Platform Admin membership or buyer. A signed provider token protects the inbox identity; it does not authorize a course, question, Purchase or Refund Request link. Recheck access at the destination. Do not put refund reasons or private question bodies in provider payloads until the data policy is decided.
2. Persist the business change before emission and retain a durable event identity. A provider idempotency window does not close the database/API dual-write gap or prevent replay after its expiry. Decide later whether a database outbox/worker is needed, how failures surface and who replays them. This research does not add infrastructure.
3. Decide which notifications are mandatory and which channels users may disable. Preferences capabilities do not settle the policy for refund decision messages. Decide whether reading the inbox can suppress email; all pricing examples assume both channels deliver.
4. Keep a single owner for each buyer email. One possible boundary is leaving existing Postmark receipt/decision sends in Cadence and sending only inbox events for those cases; another is moving their email content into orchestration and removing the direct send. These are alternatives for human choice, not simultaneous sends.
5. Preserve Cadence domain IDs and versioned event names independently of provider IDs. An SDK abstraction can help portability, but inbox read/archive state, preferences, templates, logs and retained delivery history need a separately verified export/migration approach.

## Validation still needed after the human choice

No credentials or paid access were used. Before production, verify two-user inbox isolation (including tampered tokens), role changes, unauthorized deep links, logout/user switching, React Router SSR/hydration, preference precedence, an existing buyer receipt and decision without duplicates, provider 429/5xx/timeouts, retries outside the dedupe window, bounce callbacks, deletion/export behavior and exact environment metering. Obtain contractual region/subprocessors/retention and a fresh quote at the intended volume. None of these untested items blocks this evidence report; each limits what can be claimed about an eventual integration.
